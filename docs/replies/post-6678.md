Two open-source tools for the DSH ecosystem — a diagnostics CLI and a security-check framework. Both are ordinary npm packages; nothing here needs a patched host.

**`@moonquake2004/dsh-doctor` — 40 checks in three groups**
- **env**: node / pnpm / zstd presence, `.env` shape, node-pty native binding, storages JSON, contract anchors, `.npmrc` workaround, `dsh` in PATH, settings writability, runtime zstd stability
- **profile**: bundle resolvability, entry-id collisions, patch syntax, dangling `file:` deps, named-import/export mismatch, manifest version, client bundles, dist-tag health, provenance verifiability
- **session**: orphan tool calls, unclosed turns, seq continuity, unknown event types, container frame structure, **header / first-frame integrity**, whole-store scan, migration-refusal pre-flight

It emits the `dsh-doctor/v1` envelope (name + status + exit code) so CI and support scripts consume it uniformly, and it can pull new checks from a remote catalog without a release.

**`@moonquake2004/dsh-security` — 31 checks in four layers**
- **static**: dependency audit, secret scan, sandbox/approval/permission resolution, entry poison, capability surface, poison patterns, patch-layer security-row overrides, `!!js` config-as-code, Code-Mode × sandbox mismatch, prompt-injection surface in plugin content, provenance
- **runtime** (from session logs): sandbox-violation primitives, privilege-escalation primitives, data exfiltration, plugin isolation, credential-store access
- **lifecycle**: supply-chain integrity, update integrity, reputation, release compatibility
- **secrets**: credential leak, PII exposure, sensitive output, session integrity

Plus optional integrations with four community tools (poison-guard, plugin-reducer, ecosystem; sandbox-audit retired after we found it was never published).

### The part most people actually need: when dsh will not start

Installing an incompatible plugin, or upgrading dsh against older plugins, is the most common way to end up with a host that refuses to boot — and at that point you cannot use dsh to diagnose it. These are plain Node CLI (`npx`) and **do not need dsh to boot**:

```
npx @moonquake2004/dsh-doctor --boot-check --profile web        # offline load simulation: which entry fails, and how
npx @moonquake2004/dsh-doctor --quarantine <pkg> --profile web  # move it out of the boot list → dsh starts again
npx @moonquake2004/dsh-doctor --unquarantine <pkg> --profile web
npx @moonquake2004/dsh-doctor --safe-add <pkg> --profile web    # install + verify + auto-quarantine / full rollback
npx @moonquake2004/dsh-doctor --pre-upgrade --profile web       # run before upgrading dsh
npx @moonquake2004/dsh-doctor --post-upgrade --profile web      # after: diff + load simulation + fix commands
```

`--boot-check` imports each enabled entry in a subprocess and classifies the failure (missing export / not installed / native ABI / module format / hang) — that is exactly what a boot does, so it is an explicit opt-in flag rather than default behaviour. `--quarantine` edits only the profile's boot list (it never deletes packages) and always writes a timestamped backup first.

### What this work surfaced

Everything below has a reproduction in the linked thread, not just a claim:

- **A session log's first frame must be exactly one header line**, and violating it blocks `dsh web` startup — one report had it happen three times in five days (#6651). Our own whole-store scan used to call such a log "healthy"; we treated that as a bug in our tool and fixed it.
- **Session-format drift silently disabled several runtime checks** — they matched fields that had moved, so the report read "clean" while the layer was blind. We now drive the installed migration chain itself instead of pattern-matching it.
- **`!!js` is evaluated in the host process at load** via `new Function("ctx","expr"," with (ctx) { return eval(expr) }")`, outside the agent sandbox. Two plugins on our machine use it; we published a dossier and opened an issue upstream.
- **A profile manifest with a `name` but no `version` throws** in the package inventory as soon as a loose local module is resolved (#6667) — and the manifest the harness itself generates has exactly that shape.

### Interop and posture

- We implement and consume the `dsh-doctor/v1` envelope, and follow the v1 vocabulary alignment for check names and severities (#1719). What we could not verify is published as unverified.
- Both repos have a `SECURITY.md` and **GitHub private vulnerability reporting enabled**. We treat **false negatives** (a check that silently stops matching after a field moves) and **high-noise false positives** as vulnerabilities of the tool — both end with the operator ignoring it.

**Honest limits**: most checks are static/offline; we cannot verify Windows-specific behaviour from macOS (CI now runs Ubuntu + Windows × Node 22/24, which immediately found a real Windows-only bug in one check); the runtime checks read the latest *settled* session, so they deliberately do not judge the session you are in right now.

Counterexamples, wrong-verdict reports and corrections are the most useful thing you can send. Check lists and sources: [dsh-doctor](https://github.com/moonquake2004/dsh-doctor) · [dsh-security](https://github.com/moonquake2004/dsh-security)

### 大多数人真正需要的那部分：dsh 起不来时怎么办

**装了个不兼容的插件**，或**升级 dsh 后与旧插件不兼容**，是最常见的"宿主拒绝启动"来源——而那时你已经没法用 dsh 自己来诊断。下面这些是普通 Node CLI（`npx` 直跑），**不需要 dsh 能启动**：

```
npx @moonquake2004/dsh-doctor --boot-check --profile web        # 离线模拟装载：哪条 entry 炸、炸在哪类
npx @moonquake2004/dsh-doctor --quarantine <包名> --profile web  # 摘出启动列表（先备份）→ dsh 可以起来了
npx @moonquake2004/dsh-doctor --unquarantine <包名> --profile web
npx @moonquake2004/dsh-doctor --safe-add <包名> --profile web    # 装完即验；坏了自动隔离 / 必要时整体回滚
npx @moonquake2004/dsh-doctor --pre-upgrade --profile web       # 升级 dsh 前记基线
npx @moonquake2004/dsh-doctor --post-upgrade --profile web      # 升级后：对比 + 装载模拟 + 修复命令
```

`--boot-check` 会在子进程里**真的去 import** 每条启用的 entry，并归类失败原因（缺导出 / 没装全 / 原生 ABI 不匹配 / 模块格式 / 顶层卡死）——这正是"启动"本身的语义，所以它是**显式开关**而非默认行为。`--quarantine` 只改 profile 的启动列表（**从不删除任何包**），且必定先写带时间戳的备份。

### 这轮工作暴露出的东西

下面每一条都在对应帖子里有复现，不只是结论：

- **会话日志的第一个 zstd 帧必须恰好只有一行（头行）**，违反它会直接阻断 `dsh web` 启动——有报告 5 天内遇到 3 次（#6651）。我们自己的全库扫描此前会把这种日志报成"健康"，我们把那当作**我们工具自己的 bug** 修掉了。
- **会话格式漂移曾让多项运行时检查静默失效**：它们匹配的字段已经搬走，于是报告显示"干净"，而那一层其实是瞎的。现在我们改为**驱动已装的迁移链本身**，而不是模式匹配它。
- **`!!js` 是在宿主进程内、沙箱之外于加载期求值的**（`new Function("ctx","expr"," with (ctx) { return eval(expr) }")`）。本机有两个插件在用它；我们发布了分析档并向上游提了 issue。
- **profile manifest 有 `name` 但没有 `version`**，会在解析到"游离本地模块"时让 package inventory 抛错（#6667）——而 harness 自己生成的 manifest 恰恰是这个形状。

### 互通与安全姿态

- 我们实现并消费 `dsh-doctor/v1` 信封，检查名与严重度遵循 v1 词汇表对齐（#1719）。**我们没能验证的内容，一律标注为未验证。**
- 两个仓库都有 `SECURITY.md`，并**已开启 GitHub 私有漏洞报告**。我们把**假阴性**（检查因字段搬走而静默失配）与**高噪声假阳性**都当作工具的漏洞——两者的终点都是"用户开始忽略它"。

**如实说明边界**：多数检查是静态/离线的；我们在 macOS 上无法验证 Windows 特有行为（CI 现已覆盖 Ubuntu + Windows × Node 22/24，加上的第一次就抓出一个真实的"仅 Windows"缺陷）；运行时检查读的是**最近一个已停止写入**的会话，因此有意不去评判你正在进行的这一场。

**最有用的反馈是反例、误判报告与纠正。** 检查清单与源码：[dsh-doctor](https://github.com/moonquake2004/dsh-doctor) · [dsh-security](https://github.com/moonquake2004/dsh-security)

### 一个具体例子：一条社区评论怎样删掉了我们的一个误报

介绍帖里说"我们把误报当漏洞"是个主张；这里给一个有编号、有日期的实例，因为它就发生在本贴的评论区。

**1. 提案与提醒。** @ciceroyang 在本贴提议增加一个检查（已装插件声明的 host peer 范围 vs 实际提供的核心版本），并附了一条提醒：DSH 生态几乎全在预发布上，而 **strict semver 的预发布规则要求"比较器与被判版本处于同一 `[major,minor,patch]` 元组"才允许匹配**，于是在全员 rc 的生态里会产生误报 —— `>=0.1.0-rc.5 <0.2.0` 应当**接受** `0.1.5-rc.2`，字面规则却会**拒绝**。

**2. 我们用真 node-semver 复核，他说得对：**
```
satisfies('0.1.5-rc.2', '>=0.1.0-rc.5 <0.2.0')      → false   ← 应接受（字面规则误报）
satisfies('0.1.5-rc.2', '>=0.1.0-rc.5 <0.1.0-rc.7') → false   ← 一致（确实越界）
satisfies('0.1.5-rc.2', '>=4.0.0')                   → false   ← 应记"未知"
```

**3. 而我们的代码正是这样写的。** `dsh-security` 的 SP5 判定"插件声明的核心范围是否接受实际安装的核心"时，直接调 `satisfies(..., { includePrerelease: false })` —— 因此它**会把一个健康的插件报成"不支持当前核心"**。这不是别人的坑，是我们自己的：`SECURITY.md` 里我们把"误报健康环境（用户因此开始忽略工具）"明确列为工具的漏洞，而它正发生在同一时刻我们发出去的版本里。

**4. 改法**（两条一起，避免两个组件用不同语义）：

- `checkRange` 改为**三态 + rc 规则**：区间含任何预发布比较器 → 按数值判定（接受 `0.1.5-rc.2`，拒绝越界者）；**纯 release 区间面对预发布安装版本 → `unknown`**；SP5 只对 `unsatisfied` 生成发现，`unknown` 既不算兼容也不报。
- 他提议的检查落成 **P19**（`dsh-doctor` profile 组，默认运行即覆盖，不必带 `--security`），并逐条照做他列的坑：只取 `@deepseek-ai/*`、host 版本**跟随软链接**（`file:`/dev 安装与共享镜像根都是软链接，用 lstat 风格会误报）、作用域名按第一段斜杠切、三态。他自己的真实案例现在可复现：`dsh-win32` 声明 `>=0.1.0-rc.5 <0.1.0-rc.7` 而实际提供 `0.1.5-rc.2` → 报出。

**5. 回归测试里有两条是"**不得**误报"**（正是上面第 2 步的第一、三行），另有一条确认真实越界仍要报。`dsh-security@0.4.5`、`dsh-doctor@0.4.23` 已发布。

**我们为什么把这个写进介绍帖**：一个工具的检查质量取决于它愿不愿意承认自己报错过。这条规则不是我们想出来的，是我们写错、被社区纠正、然后改对的；把它记在公开处，比任何"高准确率"的说法都更能说明你拿到的东西是怎么维护的。规则与用例的原始实现见 @ciceroyang 的仓库（本贴评论区有链接），P19 的代码注释里也标注了出处。

### 如果只带走两条命令

前面讲了能力，这里只留"明天就能用上"的部分。

**① 装插件时直接用它来装** —— 不要让"装完才发现起不来"发生：

```bash
npx @moonquake2004/dsh-doctor --safe-add <包名> --profile <profile名>
```

装完立刻验证；坏了自动隔离它、dsh 照样能起来；隔离也救不回则整体回滚——最坏情况只是一次无害的失败尝试。

**② 升级 dsh 前记一次基线** —— 升级是最容易"升完就起不来"的时刻：

```bash
# 升级前（此时 dsh 还跑得好好的）
npx @moonquake2004/dsh-doctor --pre-upgrade --profile <profile名>

# …在这里升级 dsh…

# 升级后：自动对比核心版本与插件变化，并跑装载模拟
npx @moonquake2004/dsh-doctor --post-upgrade --profile <profile名>
#   想一步到位让 dsh 先起来：加 --auto-quarantine
```

**已经起不来了？** 三条命令，同样**不需要 dsh 能启动**：

```bash
npx @moonquake2004/dsh-doctor --boot-check --profile <profile名>       # 点名哪条 entry 炸、炸在哪类
npx @moonquake2004/dsh-doctor --quarantine <包名> --profile <profile名>  # 先备份再摘出启动列表 → 重启即可
npx @moonquake2004/dsh-doctor --unquarantine <包名> --profile <profile名>
```

**一条经验法则**：在**重启 dsh 之前**跑一次 `--boot-check`。此时 dsh 还活着，你能顺手把问题处理掉；等它起不来再查，代价总是更高。

### If you take away two commands

**① Install *through* it**, so "installed it, now nothing boots" stops happening:

```bash
npx @moonquake2004/dsh-doctor --safe-add <pkg> --profile <name>
```

It verifies immediately after installing; on failure it quarantines the offender (dsh still starts); if even that cannot save it, it rolls back to the pre-install manifest. Worst case becomes a harmless failed attempt.

**② Record a baseline before upgrading dsh** — the moment breakage is most likely:

```bash
# before (while dsh still runs)
npx @moonquake2004/dsh-doctor --pre-upgrade --profile <name>

# …upgrade dsh here…

# after: diffs the core version and plugin changes, then runs the load simulation
npx @moonquake2004/dsh-doctor --post-upgrade --profile <name>
#   add --auto-quarantine to get dsh running in the same command
```

**Already broken?** Three commands, and again **none of them needs dsh to boot**:

```bash
npx @moonquake2004/dsh-doctor --boot-check --profile <name>        # names the failing entry and its class
npx @moonquake2004/dsh-doctor --quarantine <pkg> --profile <name>  # backs up, then removes it from the boot list
npx @moonquake2004/dsh-doctor --unquarantine <pkg> --profile <name>
```

**One rule of thumb**: run `--boot-check` **before** restarting dsh. While it is still running you can fix things calmly; after it refuses to start, every step costs more.
