# 检查作者的规则（check-authoring rules）

> 这份文件不是经验总结，是**规则**。每条规则都必须配一个**可执行的机制**；
> 没有机制的规则一律视为不存在（见 §0 第 4 条）。

## §0 定律

**定律一（来源律）**：结论必须来自**来源**，不能来自模型。够不到来源就报 `unknown`。

**定律二（自洽律）**：我们对用户承诺的契约——三态判定、`unknown` 不得折叠、不适用必须带理由 skip——
**必须先在工具自身的构建过程中成立**。只在输出词汇里讲诚实，在仪表与写作过程里讲"我记得"，等于没有诚实。

这两条定律的来历是六个真实错误（2026-09-15/16），它们**根因相同**，只是"来源"不同：

| 错误 | 被当成来源的"模型" | 真正的来源 |
|---|---|---|
| S14 判错视图（#6686） | 我手上那个日志文件 | 宿主**实际读**的那条流（迁移后的内存视图） |
| SR5 成片误报（25/103） | 当时选中的**一个**会话 | **整库**样本 |
| `--boot-check` 假绿灯（#6788） | 我能枚举到的 entry | loader 的 **bundle 级**前置条件 |
| P22 与 P15 重复（#6758） | 我记忆里"我们查过什么" | **实际检查清单** |
| P18 报"没有 manifest"（#6758） | 我自己的解析代码 | **宿主的**解析代码（BOM 会抛） |
| P15 被 P0 崩溃静默（#6758） | "有检查 = 用户会看到" | 检查的**执行顺序与隔离** |

## §1 规则（每条都有机制）

### R1 来源律 → 检查必须标注并**读取**权威来源

**触发**：写任何新检查。
**要求**：注释里写明判定依据的来源，且必须是**被读取的**（宿主代码 `file:line`、数据生产者、契约文档或 issue），不是记忆或复述。
**机制**：`docs/check-inventory.md` 由引擎自动生成（含来源一栏），CI 断言其与代码一致；新增检查若清单未更新则 CI 红。
**范例**：`S13`（判据取自 harness 自身读取路径 `zlib.zstdDecompressSync`）、`E6`（三个锚点在宿主源码里的位置）——这两个从没出错。

### R2 样本律 → 读真实数据的检查必须在**全体**上验，并解释每一处命中

**触发**：任何读取会话/插件/生态清单等真实数据的检查（新增或改判据）。
**要求**：发布前在**全体**上跑一遍；**每一处命中都必须能解释为真阳性或已知误报**；无法解释就不得发布。
**机制**：`scripts/corpus-run.sh` 作为发布闸门，输出必须含**分母**（"扫了 N，命中 M"）。

### R3 覆盖律 → "没看" ≠ "通过"

**触发**：任何 `pass`。
**要求**：`pass` 必须报告**检查了多少对象**；`examined === 0` 一律降为 `skip`（"无可检查对象"）。
**机制**：引擎内的 `report()` 不变量（已落地，2026-09-16）+ CI 测试断言空环境下
`examined === 0 却 pass` 为 0、且**未报告覆盖量的 pass 为 0**。

### R4 隔离律 → 一项检查的失败不得掩盖其余检查

**触发**：任何读取外部产物的检查。
**要求**：外部读取**不得抛出**（坏输入要变成结论，不是异常）；早期失败不得中断整段检查。
**机制**：回归测试喂入畸形输入（BOM / 截断 JSON / 空文件 / 坏 YAML），断言**检查总数不减少**且目标检查仍报出。

### R5 唯一归属律 → 同一事实只有一个归属

**触发**：新增检查之前。
**要求**：先查清单；提交里必须写明"已有哪条覆盖它"或"为什么没有"。重复的检查要**撤销并合并**，不是并存。
**机制**：`docs/check-inventory.md`（按 id + 一行范围 + 来源排序）；人工/自动比对范围重叠。

### R6 接口律 → 改签名前先读实际调用点

**触发**：修改 `report()` 等公共函数的参数。
**要求**：不凭记忆拼参数；先读出真实调用点的参数个数与类型。
**机制**：`report()` 对自己的参数做类型校验并**立即抛错**（`examined` 非 number/undefined、`src` 非 string/undefined 等），
让错误在测试里第一次运行就暴露，而不是变成一条静默的错误判定。

### R8 断言强度律 → 断言的强度不得超过证据（**2026-09 复查后新增**）

**触发**：写下任何面向用户的断言（含公告、release note、issue 回复）。
**要求**：分清三种证据强度并如实标注——**复现过** > **读过宿主代码** > **推断**；一个平台 ≠ 全部平台，一个样本 ≠ 全体，
机制存在 ≠ 机制足够。
**机制**：机制暂缺（**这是本文件里唯一没有机制的一条**，故明确标注为待补）。
**来历**：复查中发现我在 CHANGELOG 里写"`P22`/`P15` 重复那件事**由此可被拦住**"——但清单机制只强制一次可见 diff，
**并不检测范围重叠**。这正是本条要防的：把"机制存在"说成"机制足够"。

### R9 版本漂移律 → 宿主收紧前置条件后，必须重验 fixture 的真实性（**2026-09 复查后新增**）

**触发**：宿主（dsh）升级之后。
**要求**：先假设**fixture 失真**而不是代码坏了——0.1.6-alpha.1 收紧 loader 后，我们多个"以前能跑"的 fixture
（插件缺 `dsh.bundle`）**悄悄变成了不合法输入**，测试还绿着，但它模拟的形态宿主已不再接受。
**机制**：机制暂缺（待补：升级后跑一次全套，fixture 失败先按"真实性"复核）。

### R7 可证伪律 → "如果这条检查完全坏了，它会打印什么？"

**触发**：每条检查写完时。
**要求**：若"完全坏掉"的输出与"健康"的输出相同，这条检查就是**不可证伪**的，必须修（通常是补分母、补 skip 条件或补负例）。
**机制**：R3/R4 的测试就是它的自动形式；新检查必须至少有一条"零对象"或"坏输入"用例。

| 复查项 | 结论 |
|---|---|
| `--boot-check` 的假绿灯真的修好了吗？ | **没有**。R3 的不变量只写在 `report()` 里，而 `--boot-check` **不走 `report()`** —— 我修的是 #6788 的**具体形态**，没修这一类。实测它对空启动列表仍打印"✓ 所有可探测 entry 均可导入" |
| 同一缺陷还有几处？ | **共三处输出路径**：`--boot-check`、`--safe-add`（还会写"已知良好"快照 → 把"未验证"固化成"已验证"）、`--post-upgrade`（同样写快照）。已改为**唯一判定入口 `bootVerdict()`**，三处统一 |
| 清单机制够不够？ | **不够**。清单曾**缺 8 个动态构造的 id**（`E1-*`/`E7`/`E8`/`E9`/`E11`/`P6-patch-name-space`）→ 已补为 51 项、缺失 0；但**范围重叠仍无自动检测**（见 R8 来历） |
| R4 隔离律落地了吗？ | **远没有**。复查 profile/env 段的读取，**14 处疑似未加保护**，抽查 3 处**全部确认在 try 之外**（`readFileSync(patchFile)`、`JSON.parse(readFileSync(.../package.json))`、`readFileSync(patchPath)`）。修好的是 manifest 那一处 |
| 我的规则集本身有缺口吗？ | **有两条**：R8 断言强度（我确实过度声称过）、R9 版本漂移（fixture 失真那次）。已补入
